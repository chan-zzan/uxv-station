# 함께 일하는 방식

> **세션을 시작할 때 이 문서를 먼저 읽는다** ([CLAUDE.md](../CLAUDE.md) 작업 규칙 9).
> *무엇을* 만드는가는 다른 문서가 담는다. 이 문서는 **어떻게 설명하고 어떻게 나눠 맡는가**만 담는다.

---

## 배경

| | |
|---|---|
| 가장 익숙한 것 | **유니티 / C#** |
| 어느 정도 아는 것 | C/C++ (아주 익숙하지는 않다) |
| 입문 단계 | **파이썬, 웹**(HTML/CSS/JS/TS/React) — 둘 다 거의 처음 |

프로그래밍 개념 자체(변수·함수·루프·객체·좌표계·게임 루프)는 설명하지 않아도 된다.
막히는 곳은 개념이 아니라 **그 언어의 문법과 생태계**다.
이 둘의 설명 속도를 같게 두면 후자가 무너진다.

---

## 설명 방식

1. **세션·단계를 시작할 때 전체 맥락 브리핑부터.**
   매일 하는 작업이 아니라 맥락을 잊는다. "A단계/B단계" 같은 내부 용어를 부연 없이 쓰지 않는다.

2. **새 함수·모듈이 나오면 `import`(또는 설치) 필요 여부를 먼저 말한다.**
   "그냥 쓰면 되는 것인지"조차 모르는 상태다. 코드만 던지면 거기서 막힌다.

3. **한 번에 한 단계씩.** 여러 개념을 한 응답에 몰아넣지 않는다.
   **문제를 눈으로 본 다음 해법을 배우는 순서**가 좋다.
   (드리프트를 실측해 보여준 뒤에 절대 스케줄을 도입한 것이 그 예다)

4. **표준 API인지 지어낸 이름인지 구분해서 말한다.**
   매개변수 이름을 표준 함수로 오해한 적이 있다. 검색해도 안 나오는 이름은 그렇다고 밝힌다.

5. **비유는 익숙한 쪽에서 끌어온다.** 유니티·C#이 기준점이다.
   (`publish_loop`은 `Update`처럼 엔진이 불러주는 것이 아니라 게임 루프 자체에 가깝다 — 같은 식)

## 역할 분담

작업 규칙 4(귀속)의 실제 운용이다.

| 무엇 | 누가 |
|---|---|
| **로직 코드** | **사용자가 직접 쓴다.** Claude는 원리 설명·구조 제시·API 안내·막힌 지점 진단·리뷰까지 |
| **핵심 알고리즘** (짐벌 안정화, Pure Pursuit) | 원리 설명 → 이해 확인 → **사용자가 구현** |
| 설정 파일·자동 생성 뼈대 | Claude가 처리 (`package.json`, `tsconfig.json`, `npm create vite` 산출물 등) |
| 문서 (ADR·일지·README) | Claude가 초안, 사용자가 확인 |

**AI 인라인 자동완성은 `.vscode/settings.json`으로 꺼둔 상태다.** 손이 기억하도록 직접 친다.

---

## 왜 이렇게 하나

이 프로젝트의 목적은 완성도가 아니라 **"설명할 수 있는가"** 다.
대신 짜준 코드는 면접에서 설명할 수 없고, 이해를 건너뛴 진도는 나중에 되돌아온다.
느려 보여도 이 방식이 목적에 맞는 최단 경로다.
