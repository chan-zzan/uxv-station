## 전체 구조

```
   웹 UI            브리지               시뮬레이터
┌──────────┐   ┌──────────────┐   ┌──────────────┐
│ React+TS │◀──│   FastAPI    │◀──│    UE5       │
│  canvas  │ WS│  (Python)    │TCP│  (C++ 중심)   │
└──────────┘──▶└──────────────┘──▶└──────────────┘
                      │
                      └── ROS2 (rclpy) ※ 나중 단계

   ※ v0에서는 UE5 자리에 스텁 퍼블리셔가 들어간다
```

## 구성 요소

| 덩어리 | 위치 | 기술 | 선택 이유 |
|---|---|---|---|
| **uxv-web** | `uxv-web/` | React + TypeScript + Vite, 지도는 `<canvas>` | 작성자 실무 스택. 가장 빠름 |
| **uxv-bridge-server** | `uxv-bridge-server/` | Python + FastAPI (WebSocket 서버) | 실무 스택. 나중에 ROS2 노드(rclpy) 겸함 |
| **uxv-stub** | `uxv-stub/` | Python 스크립트 | UE5 완성 전 가짜 차량 역할 |
| **uxv-sim** | `uxv-sim/` | UE5 — 제어 로직 C++, 배관만 Blueprint | Blueprint만이면 포폴이 약해 보임 |

## 핵심 아키텍처 결정: 브리지 중심

**UE5에 ROS2를 직접 붙이지 않는다.** (rclUE 등 플러그인은 세팅 난이도가 높고 실패 시 프로젝트가 멈춘다.)
대신 **Python 브리지가 중심**이 되어 ROS2를 담당하고, UE5와는 단순 TCP/WebSocket으로 통신한다.
실무에서도 흔히 쓰는 브리지 패턴이므로 구조적 정당성도 있다.

---

## 스텁(stub)이란

진짜가 아직 없을 때 그 자리를 대신하는 가짜.
**원을 그리며 도는 가짜 차량 하나를 흉내 내어 위치·자세·속도·짐벌각을 주기적으로 발행하는
100줄 내외의 파이썬 스크립트.**

UE5가 완성되면 스텁을 끄고 UE5를 그 자리에 꽂는다. **웹은 한 줄도 고치지 않는다.**

> **스텁 없이 UI만 만드는 것은 금지.** 뒤에 아무것도 없는 대시보드는 포폴로서 가치가 없다.

---

## 인터페이스 우선 원칙

웹을 먼저 만드는 이유는 단순히 빠르기 때문만이 아니다.
**인터페이스를 엔진과 무관하게 먼저 고정**하면, v2의 "시뮬레이터 교체 가능" 주장이
특정 엔진에서 역산한 것이 아니라 **사실**이 된다.

계약은 [00-message-contract.md](00-message-contract.md)에 있다.

## 네이밍 컨벤션

- 저장소 루트 및 `uxv-web`/`uxv-bridge-server`/`uxv-stub` 하위: **소문자 + 하이픈(kebab-case)**
  (Linux는 대소문자를 구분하므로 대문자를 섞으면 CI/서버에서 깨진다. npm 패키지명도 소문자만 허용)
- **UE5 프로젝트 내부만 예외로 PascalCase** (Epic 컨벤션). 예: `VehicleSim.uproject`

## 모노레포

혼자 하는 소규모 프로젝트이고, 포폴이므로 링크가 하나여야 하며, 메시지 계약이 한 곳에 있어야 한다.
나중에 분리하는 것은 쉽지만 합치는 것은 어렵다.
