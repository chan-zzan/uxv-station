## 기술 스택 — 세 도구의 역할

혼동하기 쉬워서 먼저 갈라둔다.

| | 무엇 | 어디서 도나 |
|---|---|---|
| **Node.js** | 브라우저 밖에서 JS를 돌리는 실행기 | 시스템. **개발 도구를 돌리는 자리** |
| **Vite** | 빌드 도구 — TS/JSX를 브라우저용 JS로 변환 + 개발 서버 | Node 위에서 |
| **React** | 화면을 코드로 기술하는 라이브러리 | 브라우저 안에서 |
| 브라우저 | 실제로 그리는 곳 | **완성품이 도는 자리** |

> **Node 위에서 Vite가 돌며, React로 쓴 코드를 브라우저에 넘긴다.**

Node와 브라우저 둘 다 JS 실행 환경이지만 역할이 갈린다 — Node는 개발 도구용, 브라우저는 완성품용.
**배포하면 Node와 Vite는 빠지고 정적 파일만 남는다.**

명령은 사실상 둘뿐이다.

| 명령 | 하는 일 |
|---|---|
| `npm run dev` | 개발 서버 (`localhost:5173`). 변환 + 서버 + 저장 시 즉시 반영(HMR)을 겸한다 |
| `npm run build` | 타입 검사(`tsc -b`) 후 `dist/`에 배포용 뭉치 |

**`dev`는 타입 검사를 하지 않는다.** 타입 에러가 있어도 개발 서버는 돈다.
검사는 VS Code의 빨간 줄과 `npm run build`가 한다.

## 실행 흐름 — 누가 누구를 부르나

```
브라우저
  │  ① 이 파일을 연다
  ▼
index.html              빈 상자 <div id="root"> + main.tsx 불러오기
  │  ②
  ▼
src/main.tsx            React를 그 빈 상자에 붙인다          [진입점]
  │  ③
  ▼
src/App.tsx             화면 배치 — 왼쪽 지도 / 오른쪽 패널   [레이아웃]
  │  ④ view를 넘기며 심는다
  ▼
src/MapCanvas.tsx       <canvas>를 만들고 매 프레임 호출     [배관]
  │  ⑤ 초당 60번
  ▼
src/draw.ts             격자·차량을 그린다
  │  ⑥ "이 월드 좌표는 화면 어디?"
  ▼
src/transform.ts        월드(m) ↔ 화면(px) 변환
```

흐름에 끼지 않고 옆에서 참조되는 것 둘:

```
src/contract.ts         메시지 타입 정의   ← draw·transform·(나중에) 통신부
src/index.css           스타일            ← main.tsx가 한 번 불러오면 전체 적용
```

## `src/` 파일별 역할

| 파일 | 역할 | 한 문장 |
|---|---|---|
| `main.tsx` | **진입점** | React를 `index.html`의 빈 상자에 붙인다. 앱 전체에서 한 번만 실행 |
| `App.tsx` | **레이아웃** | 화면을 지도(왼쪽)와 패널(오른쪽)로 나눈다 |
| `MapCanvas.tsx` | **배관** | `<canvas>` 크기·해상도를 맞추고, 매 프레임 지우고 `drawFrame`을 부른다 |
| `draw.ts` | **그리기** | 격자·축·차량을 실제로 그린다 |
| `transform.ts` | **좌표 변환** | 월드(m, ENU) ↔ 화면(px, canvas) |
| `contract.ts` | **계약 타입** | 주고받을 JSON의 모양. 실행되는 코드가 아니다 |
| `index.css` | **스타일** | 색·크기·배치 |

## 왜 이렇게 나눴나

### `transform.ts`를 따로 뺀 이유

계약 문서의 **"변환은 가장자리에서만 한다"** 를 파일 경계로 만든 것이다.
**좌표계가 다르다는 사실을 아는 파일이 하나뿐**이어야, 부호 버그가 났을 때 볼 곳이 한 곳이다.

맞춰야 할 어긋남은 셋이다.

| | 계약 (ENU) | canvas |
|---|---|---|
| 단위 | 미터 | 픽셀 |
| 원점 | 맵 로컬 원점 | 캔버스 좌상단 |
| y 방향 | **북쪽(위)이 +** | **아래가 +** |

`draw.ts`는 전부 월드 좌표(m)로 생각하고, 화면에 찍기 직전에만 `worldToScreen`을 통과시킨다.
격자 코드 안에서 픽셀을 직접 계산하기 시작하면 변환을 한 곳에 모은 의미가 없어진다.

### `MapCanvas.tsx`와 `draw.ts`를 가른 이유

- `MapCanvas` = **엔진 쪽.** 캔버스 버퍼 크기 맞추기, 고해상도(devicePixelRatio) 보정,
  매 프레임 지우기, `requestAnimationFrame` 루프
- `draw` = **스크립트 쪽.** 무엇을 그릴지

유니티로 치면 `MapCanvas`가 `Update`를 불러주는 엔진이고 `draw`가 그 안의 스크립트다.
[03-working-style.md](03-working-style.md)의 역할 분담과 경계가 같다 — **배관은 Claude, 로직은 작성자.**

`ctx`의 좌표 단위를 CSS 픽셀로 고정하는 것도 `MapCanvas`가 한다.
해상도 배율을 `setTransform`으로 한 번만 처리해서, `draw.ts`가 그 존재를 모르게 한다.

### `contract.ts`가 흐름 밖에 있는 이유

**타입은 실행 시점에 존재하지 않는다.** 변환될 때 통째로 지워지고 브라우저에는 남지 않는다.

여기서 따라오는 한계가 하나 있고, 통신을 붙일 때 다시 문제가 된다.

```ts
const state = JSON.parse(text) as VehicleState   // 검사하지 않는다
```

`as`는 TS에게 "이 모양이라고 치자"라고 말하는 것일 뿐 실제로 확인하지 않는다.
**TS는 우리 코드 안의 오타는 잡지만, 밖에서 들어오는 JSON은 못 잡는다.**
(Day 3의 `attitude`/`altitude` 오타와 같은 종류 — [99-devlog.md](99-devlog.md))

### `mode`를 `enum`이 아니라 문자열 유니온으로 둔 이유

```ts
export type VehicleMode = 'IDLE' | 'AUTO' | 'EMERGENCY_STOP' | 'LINK_LOST'
```

TS의 `enum`은 내부적으로 숫자나 별도 객체라 JSON으로 나갈 때 변환이 필요하다.
문자열 유니온은 **값이 문자열 그 자체**라 계약의 `"mode": "AUTO"` 와 1:1로 맞는다.
계약이 JSON이므로 계약을 그대로 베낀 쪽을 골랐다.

## `uxv-web/` 바깥 파일

### 의미 있는 것

| 파일 | 역할 | 손댈 일 |
|---|---|---|
| `index.html` | 브라우저가 여는 진짜 시작점. `<div id="root">` 하나뿐 | 거의 없음 |
| `package.json` | 쓰는 패키지 목록 + `npm run` 명령 별명 | 패키지 추가 시 (명령이 자동으로 고침) |
| `package-lock.json` | 실제 설치된 버전 못박음. **git에 올린다** | 손으로 고치지 않음 |
| `vite.config.ts` | Vite 설정 | 거의 없음 |

`package.json`의 버전 표기는 범위다 (`^19.2.8` = 19.2.8 이상 20 미만).
그래서 사람마다 다른 버전이 깔릴 수 있고, **그걸 고정하려고 `package-lock.json`이 있다.**

### 있는 줄만 알면 되는 것

| 파일/폴더 | 역할 |
|---|---|
| `tsconfig.json` | 아래 둘을 가리키는 목차 |
| `tsconfig.app.json` | **`src/` 코드의 TS 규칙.** `noUnusedParameters` 등이 여기 |
| `tsconfig.node.json` | 설정 파일 자신(`vite.config.ts`)의 TS 규칙 |
| `.oxlintrc.json` | 문법 검사 설정 |
| `node_modules/` | 설치된 패키지. git 제외. 지워도 `npm install`로 복구 |

> **TS 설정이 셋으로 쪼개진 이유**: `src/` 코드는 브라우저에서 돌고 `vite.config.ts`는 Node에서 돈다.
> 실행 환경이 달라 쓸 수 있는 기능이 다르므로, 한 설정으로 묶으면 규칙이 섞인다.

## 웹 v0 작업 조각

로드맵 9장의 웹 v0 범위 5개 항목을 의존 순서대로 자른 것.

| | 조각 | 내용 | 데이터 출처 |
|---|---|---|---|
| **W1** | 지도 좌표계 | 뼈대 + 격자 캔버스 + `worldToScreen`/`screenToWorld` | 없음 |
| **W2** | 차량 렌더 + 패널 | 차량 아이콘·헤딩, 텔레메트리 패널 | **로컬 가짜 상태** |
| **W3** | 실제 연결 | 브리지(FastAPI) + 스텁 WS 송신 + 연결상태/하트비트 1초 | WebSocket |
| **W4** | 명령 | 지도 클릭 → `SetWaypoints` 전송 | 양방향 |

### W2를 "로컬 가짜 상태"로 시작하는 이유

브라우저 안에서 `t`를 굴려 `VehicleState`를 만들어내는 함수 하나를 두고,
W3에서 그 자리에 WebSocket 수신을 꽂는다. **렌더링 코드는 한 줄도 바뀌지 않는다.**

1. **버그 원인이 줄어든다.** 브리지·WS·스텁을 동시에 세우고 화면이 비면 원인 후보가 여섯이다
   (스텁 송신 / 브리지 수신 / 중계 / 웹 수신 / 파싱 / 그리기). 가짜 상태면 후보가 하나다
2. **다음 단계의 판정이 명확해진다.** 화면이 이미 돌고 있으면, W3에서 검증할 대상은 통신뿐이다
3. **v2 주장의 증거가 된다.** 같은 자리에 가짜 상태 → WebSocket → (나중에) UE5를 꽂아본 이력 자체가,
   [01-architecture.md](01-architecture.md)의 "인터페이스 우선 원칙"이 말뿐이 아니라는 근거다

로드맵 5장의 *"스텁 없이 UI만 만드는 것은 금지"* 는 **최종 산출물** 기준이지 개발 순서가 아니다.
