## 1. 프로젝트 개요

**무인 차량 통합관제 데모.** 시뮬레이터 + 통신 브리지 + 웹 운용통제기를 한 덩어리로 구현한다.

- 웹 운용통제 UI에서 무인차량에 임무를 지시하고 상태를 감시한다
- 차량은 시뮬레이터(UE5) 안에서 실제 차량 기구학에 따라 자율주행한다
- 짐벌 카메라는 차체 기동과 무관하게 지정 표적을 계속 조준한다
- 통신이 끊기면 안전 동작으로 전환한다

## 2. 배경 — 왜 이걸 만드는가

**목적: 방산 분야 경력직 이직용 포트폴리오.**

작성자는 방산 SW 개발 3년차이며, 두 갈래 경력을 갖고 있다.

- **무인차량 훈련 시뮬레이터** (Unity, 약 3년) — 원격주행/자율주행/감시·무장/통신 등 광범위 담당
- **운용통제기** (Theia/TypeScript + FastAPI/Python + ROS2 연동, 진행 중)

문제는 이 둘이 따로 놀아서 커리어 서사가 안 잡힌다는 것. **이 프로젝트는 그 둘이 왜 한 사람 안에
있는지를 하나의 산출물로 증명하기 위한 것이다.**

타겟 직무는 무인체계 SW / 통합관제·지휘통제 / 디지털트윈 시뮬레이터 계열이며,
업계에서 실제로 진행 중인 과제들(다중 무인 플랫폼 통합관제, 디지털트윈 기반 검증 시뮬레이터)과
같은 모양을 축소판으로 만드는 것이 설계 의도다.

**또 하나의 목적: 귀속(歸屬)의 증명.**
기존 실무 산출물은 AI 도구 기여분이 커서 "어디까지가 내 판단인가"가 흐릿하다.
이 프로젝트는 지금 처음부터 만들기 때문에, 온전히 본인 것이라고 말할 수 있는 유일한 자산이다.
그래서 **"설명할 수 있는가"가 완성도보다 우선한다.**

## 3. 절대 규칙 (반드시 준수)

### 보안
- **회사 자료를 이 저장소에 절대 넣지 않는다.** 실무 프로젝트 코드, 케이스 스터디 초안,
  워크스루 문서, 스크린샷 등 일체 금지. 별도 비공개 폴더에 물리적으로 분리 보관한다.
- 이 저장소는 공개를 전제로 한다. 실제 장비 명칭, 군 제원, 실제 통신 규격, 실 IP/포트 등을
  쓰지 않는다. 모든 것은 일반적인 "무인 차량"으로 추상화한다.

### 무결성
- **직접 이해하지 못한 코드는 남기지 않는다.** AI에게 학습·API·구조·디버깅은 적극적으로 묻되,
  핵심 알고리즘과 설계 판단은 본인 소유여야 한다.
- 기준: **"코드를 전부 지우고 처음부터 다시 만들 수 있고, 모든 설계 결정을 설명할 수 있는가."**
- 특히 짐벌 안정화와 경로 추종 제어기는 화이트보드에 유도해서 설명할 수 있어야 한다.

### 범위
- **v1 완료 기준(4장)을 넘어서는 기능을 추가하지 않는다.** 아이디어가 생기면 구현하지 말고
  `docs/02-roadmap.md`에 적는다.
- 작성자는 범위를 넓히다 미완성으로 끝내는 경향이 있다. **완성 > 화려함.**
- UI 라이브러리 선정, 프로젝트 이름, 폴더 구조 같은 결정에 시간을 태우지 않는다.

### 시간 제약
- 평일 저녁 2~3회 × 1시간 수준. **주말은 작업하지 않는다.**
- 매주 "돌아가는 것"을 남긴다. 완성이 아니라 진전 단위로 자른다.

## 4. v1 확정 스펙 및 완료 기준

### 완료 기준 (이걸 만족하면 v1 종료. 더 하지 않는다)

> 웹 UI 지도에 웨이포인트를 찍으면 → **A\***로 경로가 생성되고 → UE5 안의 차량이
> **Pure Pursuit**로 경로를 추종하며 주행한다(곡률 기반 감속 포함).
> 주행 중 **화면에서 표적을 지정하면 짐벌이 차체 기동과 무관하게 그 표적을 계속 조준**한다.
> **통신이 끊기면 하트비트 타임아웃으로 안전 정지**한다.
>
> **산출물: 2분 데모 영상 + README**

### 포함 / 제외

| 항목 | v1 | 비고 |
|---|---|---|
| 웨이포인트 경로계획 (A*) | 포함 | 격자 지도 기반 |
| 경로 추종 (Pure Pursuit) | 포함 | 곡률 기반 감속 |
| 짐벌 안정화 — L1 표적지정 추적 | 포함 | 데모의 하이라이트 |
| 하트비트 타임아웃 → 안전 정지 | 포함 | 최소한의 통신 신뢰성 |
| 짐벌 — L2 자동탐지 | 제외 | v2 이후 |
| 재밍/SNR/무선침묵 통신 모의 | 제외 | v2 이후 |
| 차량 2대 이상 | 제외 | v2/v3 |
| 실제 지도(위경도) | 제외 | v1 후반 또는 v2 |

### 짐벌 목표 계층 (참고)

- **L0** 지점 지향 — 지도에서 좌표 클릭, 짐벌이 그 월드 좌표를 지향
- **L1** 표적 지정 추적 — 화면 속 개체 클릭, 개체가 움직여도 조준 유지 ← **v1은 여기까지**
- **L2** 자동탐지 — 화면 내 개체 자동 나열 및 우선순위 (v2 이후)

L2는 ML 비전이 아니라 **가상 개체 목록 + 콜라이더 다면 가시성 판정** 방식으로 구현한다.
저렴하고, 본인이 완전히 설명할 수 있기 때문이다.

## 5. 아키텍처 및 기술 스택

```
   웹 UI            브리지               시뮬레이터
┌──────────┐   ┌──────────────┐   ┌──────────────┐
│ React+TS │◀──│   FastAPI    │◀──│    UE5       │
│  canvas  │ WS│  (Python)    │TCP│  (C++ 중심)   │
└──────────┘──▶└──────────────┘──▶└──────────────┘
                      │
                      └── ROS2 (rclpy) ※ 나중 단계
                      
   ※ v0에서는 UE5 자리에 스텁 퍼블리셔가 들어간다
```

| 덩어리 | 기술 | 선택 이유 |
|---|---|---|
| **uxv-web** | React + TypeScript + Vite, 지도는 `<canvas>` | 작성자 실무 스택. 가장 빠름 |
| **uxv-bridge-server** | Python + FastAPI (WebSocket 서버) | 실무 스택. 나중에 ROS2 노드(rclpy) 겸함 |
| **uxv-stub** | Python 스크립트 | UE5 완성 전 가짜 차량 역할 |
| **uxv-sim** | UE5 — 제어 로직 C++, 배관만 Blueprint | Blueprint만이면 포폴이 약해 보임 |

### 핵심 아키텍처 결정: 브리지 중심

**UE5에 ROS2를 직접 붙이지 않는다.** (rclUE 등 플러그인은 세팅 난이도가 높고 실패 시 프로젝트가 멈춘다.)
대신 **Python 브리지가 중심**이 되어 ROS2를 담당하고, UE5와는 단순 TCP/WebSocket으로 통신한다.
실무에서도 흔히 쓰는 브리지 패턴이므로 구조적 정당성도 있다.

### 스텁(stub)이란

진짜가 아직 없을 때 그 자리를 대신하는 가짜. **원을 그리며 도는 가짜 차량 하나를 흉내 내어
위치·자세·속도·짐벌각을 주기적으로 발행하는 100줄 내외의 파이썬 스크립트.**
UE5가 완성되면 스텁을 끄고 UE5를 그 자리에 꽂는다. 웹은 한 줄도 고치지 않는다.

**스텁 없이 UI만 만드는 것은 금지.** 뒤에 아무것도 없는 대시보드는 포폴로서 가치가 없다.

## 6. 기술 결정과 근거

> 아래 내용은 `docs/decisions/` 에 ADR로 옮겨 적는다.
> **결정할 때마다 5~10줄씩 실시간으로 기록한다** — 선택지, 고른 것, 이유, 포기한 것.
> (과거 프로젝트에서 "왜 그렇게 했는지"가 기억나지 않아 고생한 경험이 있으므로.)

### 자율주행: NavMeshAgent를 쓰지 않는다
- NavMesh는 게임 캐릭터 이동 방식이라 **조향각 제한, 최소 회전반경 등 차량 기구학을 무시**한다.
  제자리 회전이 가능해지는 등, 무인체계 종사자가 보면 바로 알아본다. "게임 개발자"로 읽힌다.
- 대신 실제 자율주행 스택 구조를 따른다:
  **차량 모델**(Ackermann 또는 skid-steer, UE5 Chaos Vehicle 물리 기반)
  → **전역 경로계획**(A*, 차량 제약 반영 시 Hybrid A*)
  → **경로 추종**(Pure Pursuit)
  → **속도 프로파일**(곡률 기반 감속)

### 경로 추종: Pure Pursuit
- 핵심 로직이 50~100줄로 짧다
- 수식이 단순해 **화이트보드에 유도해서 설명 가능** — 무결성 원칙에 부합
- 실제 자율주행에서 쓰이는 기법
- **lookahead distance 튜닝 트레이드오프**(짧으면 진동, 길면 코너를 자름)가
  그 자체로 케이스 스터디의 "판단" 재료가 된다

### ROS2 Nav2를 쓰지 않는다
- 학습 비용이 크고, 남의 스택을 쓰면 다시 귀속 문제가 생긴다
- **"Nav2가 있는 것은 알지만 제어기를 직접 이해하려고 구현했다"**가 더 좋은 답변이다

### v0에서는 ROS2 도입을 미룬다
- Windows에서 WSL2 + ROS2 세팅은 저녁 두세 번이 날아갈 수 있고, 거기서 좌절하면 착수 자체가 무산된다
- **v0는 WebSocket 직결**로 가고, ROS2는 UE5를 붙이는 단계에서 도입한다
- 단, **메시지 구조는 처음부터 ROS2로 옮기기 쉽게** 설계한다

### 웹을 먼저 만든다
- TypeScript/웹이 작성자의 최강 스택이라 1~2주 내 가시적 결과 → 모멘텀 확보
- 더 중요한 이유: **인터페이스를 엔진과 무관하게 먼저 고정**하면,
  v2의 "시뮬레이터 교체 가능" 주장이 특정 엔진에서 역산한 것이 아니라 **사실**이 된다

### 지도는 실제 지도(위경도)를 쓰지 않는다 (v1 초반)
- UE5 맵은 가상 지형이라 위경도가 없다. 실제 지도를 깔면 좌표 변환부터 씨름하게 된다
- **2D `<canvas>`에 격자 평면도 + 로컬 좌표(미터)** 로 시작. 100줄이면 충분
- 위경도 ↔ 로컬 좌표 변환은 나중에 붙이면 오히려 이야깃거리가 된다

## 7. 메시지 계약 초안

> **이 프로젝트의 뼈대.** 웹·브리지·스텁·UE5가 모두 이 계약만 바라본다.
> 완벽하게 만들려 하지 말 것. 바뀌는 것을 전제로 하며, 바뀌는 과정 자체가 나중에 쓸 이야기다.

```
[차량 → 관제기]  (10Hz)

  VehicleState
    timestamp
    position   : x, y, z            (로컬 좌표, m)
    attitude   : yaw, pitch, roll   (rad)
    velocity   : linear, angular
    gimbal     : pan, tilt          (rad)
    mode       : IDLE | AUTO | EMERGENCY_STOP | LINK_LOST
    
  Heartbeat
    timestamp


[관제기 → 차량]

  SetWaypoints
    points : [(x, y), ...]
    
  SetGimbalTarget
    type   : POINT | ENTITY
    value  : (x, y, z) 또는 entity_id
    
  EmergencyStop
```

메시지 계약이 한 곳에 있어야 한다. 나중에 분리하는 것은 쉽지만 합치는 것은 어렵다.

  (Linux는 대소문자를 구분하므로 대문자를 섞으면 CI/서버에서 깨진다. npm 패키지명도 소문자만 허용)
- **UE5 프로젝트 내부만 예외로 PascalCase** (Epic 컨벤션). 예: `VehicleSim.uproject`

## 9. 작업 순서

```
[1] 웹 UI + 스텁 퍼블리셔      ← 지금 여기
[2] UE5 짐벌 안정화
[3] 차량 물리
[4] A* / Pure Pursuit
[5] 스텁 제거, UE5로 대체
```

### 웹 v0 범위 (2주 캡, 디자인 말고 기능만)

- 격자 지도(canvas) 위 차량 아이콘 + 이동 표시
- 텔레메트리 패널: 위치 / 속도 / 자세 / 짐벌각 / 연결 상태
- 지도 클릭 → 웨이포인트 명령 전송
- **하트비트 표시** — 스텁을 끄면 "통신두절" 표시되고 정지 상태로 전환
- 스텁 퍼블리셔 (원을 그리며 도는 가짜 차량)

**못생겨도 된다.** UI 라이브러리 선정에 시간을 태우는 것이 가장 흔한 실패다.

## 12. Claude Code 작업 지침

1. **3장 절대 규칙을 항상 우선한다.** 특히 보안(회사 자료 금지)과 범위(v1 완료 기준 초과 금지).
2. **작성자가 이해하지 못한 채로 코드를 늘리지 않는다.** 핵심 알고리즘(짐벌 안정화, Pure Pursuit)은
   구현 전에 원리를 설명하고, 작성자가 이해했는지 확인한 뒤 진행한다.
   막히면 코드를 대신 써주기보다 **작성자가 직접 쓸 수 있게 유도**한다.
3. **결정이 생기면 `docs/decisions/`에 ADR을 남기도록 제안한다.**
4. **범위가 늘어나는 제안이 나오면 구현하지 말고 `docs/02-roadmap.md`로 보낸다.**
5. 한 번에 한 단계씩. 9장 순서를 건너뛰지 않는다.
6. 매 작업 세션 끝에 "이번에 돌아가게 된 것"을 한 줄로 정리한다.
