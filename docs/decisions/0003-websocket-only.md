# ADR 0003 — v1 전송은 WebSocket 하나로 통일한다

- **상태**: 채택
- **날짜**: 2026-07-24
- **맥락**: 로드맵 5장에 "UE5와는 단순 TCP/WebSocket으로 통신한다"고만 되어 있어 미확정이었다

---

## 선택지

| | 웹 ↔ 브리지 | UE5 ↔ 브리지 |
|---|---|---|
| **WebSocket** ← 채택 | 가능 | 가능 |
| 생 TCP | **불가** (브라우저가 소켓을 못 연다) | 가능 |
| UDP | **불가** | 가능 |
| ROS2 (DDS) | **불가** (브라우저에 DDS가 없다) | 가능 |

## 고른 것

**v1은 WebSocket 하나로 통일한다.** 스텁도 UE5도 웹도 전부 같은 프로토콜을 쓴다.

```
   UE5 / 스텁 ──WS──▶  ┌─────────────┐
                       │   브리지     │  :8000  (유일한 서버)
   웹 (브라우저) ──WS──▶ └─────────────┘
```

## 이유

- **웹 쪽은 사실상 선택지가 없다.** 브라우저는 보안상 생 TCP/UDP 소켓을 열 수 없고,
  실시간 양방향이 필요하므로 REST(요청-응답)나 SSE(단방향)로는 안 된다.
- **UE5 쪽은 자유롭지만 통일이 이득이다.** 스텁과 UE5가 같은 프로토콜을 쓰면
  [5]단계에서 스텁을 끄고 UE5를 꽂을 때 **브리지를 한 줄도 고치지 않는다.**
  로드맵 5장의 "스텁을 끄고 UE5를 그 자리에 꽂는다"가 말 그대로 성립한다.
  다른 프로토콜을 쓰면 브리지가 서버를 두 종류 돌려야 한다.
- **WebSocket은 TCP + 프레이밍이다.** 생 TCP는 바이트 흐름만 보장하고 메시지 경계를
  알려주지 않아, 길이 접두사 같은 규칙을 직접 만들고 부분 수신을 버퍼링해야 한다.
  WebSocket은 그것을 프로토콜이 처리한다.

### UDP를 쓰지 않은 이유

실제 무인체계 텔레메트리는 UDP를 쓰는 경우가 많다. TCP는 패킷이 유실되면 재전송될 때까지
뒤 데이터를 붙잡고 기다려서, 오히려 최신 위치가 늦게 도착한다. 초당 10번 오는 위치 정보는
한두 개 빠져도 다음 것이 0.1초 뒤 오므로 UDP가 합리적이다.

**그러나 v1 데모는 전부 localhost에서 돈다.** 유실이 사실상 없으므로 UDP의 이점이 없고,
복잡도만 늘어난다. 실제 무선 링크였다면 텔레메트리는 UDP, 명령은 TCP로 나눴을 것이다.

## 방침 — 전송 계층을 갈아끼울 수 있게 짠다

**핵심 로직이 전송 방식을 모르게 만든다.**

```
 ┌──────────────────────────┐
 │  핵심 로직                 │  상태 보관, 명령 검증, 하트비트 감시
 │  (전송 방식을 모름)         │
 └──────────┬───────────────┘
 ┌──────────┴───────────────┐
 │  전송 어댑터 (WebSocket)   │  ← 나중에 ROS2 어댑터를 옆에 추가
 └──────────────────────────┘
```

이렇게 두면 나중에 ROS2를 붙이는 일이 **어댑터를 하나 더 다는 것**이 된다.
잘 짜면 어차피 이렇게 나뉘므로 추가 비용은 거의 없다.

로드맵 6장이 웹을 먼저 만드는 이유로 든 논리와 같다 —
실제로 갈아끼워 봤을 때 비로소 "설계가 열려 있었다"가 주장이 아니라 **사실**이 된다.

## 포기한 것

- UDP의 실시간 이점 (localhost 환경에서는 의미 없음)
- UE5에서 프로토콜을 자유롭게 고를 여지 (통일의 대가)
- 다중 전송(ROS2 / REST) 구현은 v1 범위 밖 → [02-roadmap.md](../02-roadmap.md) 아이디어 보관함
