# ADR 0002 — 계약 좌표계는 ROS 표준 ENU를 따른다

- **상태**: 채택
- **날짜**: 2026-07-24
- **맥락**: 메시지 계약에 "로컬 좌표(m)"까지만 있고 축 방향·각도 기준이 없었다

---

## 문제

같은 상황을 우리가 붙일 세 세계가 전부 다르게 표현한다.

| | 축 | 단위 | 회전 |
|---|---|---|---|
| ROS2 | 오른손, x=동·y=북·z=위 | m | 반시계 양수 |
| UE5 | 왼손, z=위 | **cm** | 시계 양수 |
| 웹 canvas | **y가 아래로 증가** | px | — |

기준을 안 정하면 부호가 뒤집히고 90도씩 돌아가는 버그가 난다. 그리고 그때마다
"여기에 -1을 곱하면 맞네" 식으로 땜질하게 되는데, 그런 땜질이 서너 군데 쌓이면 손을 못 댄다.
무인체계에서 가장 흔하고 가장 지겨운 종류의 버그다.

## 선택지

1. **ROS 표준 ENU (REP-103)** ← 채택
2. UE5 네이티브에 맞추기
3. 웹 canvas에 맞추기 (y가 아래로)

## 고른 것

**계약 좌표계는 ROS 표준 ENU 하나로 고정하고, 변환은 가장자리에서만 한다.**

```
        y (북)
        ↑
        └───→ x (동)      z = 위

   yaw = 0 → 동쪽(+x), 반시계 양수, 범위 -π ~ +π
   길이 m / 각도 rad
```

변환 지점은 셋뿐이다.

| 경계 | 변환 |
|---|---|
| 웹 렌더링 | `worldToScreen()` / `screenToWorld()` — canvas y축 반전 |
| 웹 표시 | 라디안 → 도. **표시만** 바꾸고 저장·전송은 라디안 유지 |
| UE5 어댑터 | 왼손·cm ↔ 오른손·m ([2]단계에서 작성) |

## 이유

- **로드맵 6장에 이미 답이 있다** — *"메시지 구조는 처음부터 ROS2로 옮기기 쉽게 설계한다."*
  계약이 이미 ROS 표준이면 나중에 ROS2를 붙일 때 변환 코드가 아예 필요 없다.
- **임의 규칙이 아니라 업계 표준(REP-103)이다.** "왜 이렇게 했나"에 한 줄로 답할 수 있다.
  직접 정한 규칙은 매번 설명해야 한다.
- UE5 네이티브에 맞췄을 때의 이점(UE5에서 변환 불필요)은 **어댑터를 한 번 짜면 끝**이라 작다.
  반대로 ROS2 이식 시점에는 전부 뜯어야 한다.

### 웹 좌표 변환을 렌더링 계층에만 둔 이유

수신 즉시 화면 좌표로 바꿔 저장하는 방법도 있었지만 버렸다.
텔레메트리 패널에 위치를 표시하려면 **다시 되돌려야** 하고, 뒤집고 되뒤집는 코드가
여기저기 생기면 어느 시점의 값이 어느 좌표계인지 헷갈리기 시작한다. 원본은 원본대로 둔다.

`ctx.scale(1, -1)`로 캔버스를 통째로 뒤집는 방법도 버렸다.
**글자와 아이콘까지 거울상이 되어** 텍스트를 그릴 때마다 또 뒤집어야 한다.

변환 함수 한 쌍만 좌표계를 알고 나머지 코드는 전부 월드 좌표만 다루면,
나중에 화면 확대·이동이나 위경도 변환을 붙일 때도 그 두 함수만 고치면 된다.

### 짐벌각을 차체 기준으로 둔 이유

실제 짐벌 하드웨어가 차체 기준으로 명령받고 보고한다. 그리고 차체가 회전할 때
`pan` 값이 반대로 변하는 것 자체가 **짐벌 안정화가 동작한다는 증거**라 데모에서 보여주기 좋다.
월드 기준이면 표적이 고정일 때 숫자가 움직이지 않아 밋밋하다.
월드 기준 값이 필요하면 `yaw + pan`으로 언제든 계산된다.

## 포기한 것

- UE5와 웹 양쪽에서 각각 변환 계층을 짜야 한다 (각 한 번씩, 총 2회)
- 웹에서 좌표를 다룰 때 항상 "이건 월드 좌표"라는 의식이 필요하다
  (그 대신 변환 함수 밖에서는 좌표계를 고민할 일이 없어진다)
